# oriel-hv: a Hypervisor.framework backend experiment

The app runs guests through Virtualization.framework, which gives no way to add a custom device, such as a 3D GPU for Windows. `oriel-hv` is a small virtual machine monitor (VMM) built directly on Hypervisor.framework, where every device is our own code. It is a learning prototype, not part of the app.

**What it does today:** boots the stock Alpine `virt` aarch64 ISO to an interactive root shell, with:

- 2 vCPUs
- GICv3 interrupts
- the architected timer
- PSCI power management
- a PL011 serial console
- a virtio block disk

On an M-series Mac the login prompt appears in about 1.5 s.

```bash
Experiments/hypervisor/run.sh path/to/alpine-virt-3.24.x-aarch64.iso          # interactive; Ctrl-A then x quits
Experiments/hypervisor/run.sh path/to/alpine-virt-3.24.x-aarch64.iso --test   # boot, log in, run a command, power off
```

It needs macOS 15 or later (for the framework's GICv3) and Apple silicon. The binary is ad-hoc signed with `com.apple.security.hypervisor`.

## How it works

Hypervisor.framework gives you CPUs and memory. Everything else is the VMM's job:

| Piece | Who provides it | Where in `main.c` |
| --- | --- | --- |
| Guest RAM | `hv_vm_allocate` + `hv_vm_map` at IPA `0x40000000` | `main` |
| vCPUs | `hv_vcpu_create` / `hv_vcpu_run`, one thread each | `vcpu_thread_func` |
| Interrupt controller | The framework's GICv3 (`hv_gic_create`, macOS 15+) | `main` |
| Timer | The framework delivers the virtual timer PPI (27) itself | — |
| Hardware description | A flattened device tree built by hand | FDT builder |
| Serial console | Emulated PL011 at `0x09000000`, SPI 33 | `uart_*` |
| Disk | Emulated virtio-mmio v2 block device at `0x0A000000`, SPI 34 | `virtio_*` |
| Power and SMP | PSCI over `HVC`: `CPU_ON`, `CPU_OFF`, `SYSTEM_OFF`, … | `handle_psci` |

### The run loop

Each vCPU thread calls `hv_vcpu_run`. The guest runs natively until it does something the hardware cannot finish alone; then the call returns with an exit reason:

1. **Data abort** on an address with no RAM behind it. That is a device access: the syndrome register (ESR) tells us the size, the direction and the register, so we call the PL011 or virtio code and step the PC past the instruction.
2. **HVC.** A firmware call (PSCI): start a CPU, stop one, power off.
3. **WFI.** The guest is idle. We sleep until its timer deadline or until a device kicks it.
4. **Trapped system register.** Read as zero, writes ignored.

Linux boots exactly as on a real board: `X0` holds the device tree address and the PC holds the kernel's entry point, with the MMU off.

### Memory map

```
0x08000000  GICv3 distributor
0x09000000  PL011 UART
0x0A000000  virtio-mmio block
0x0C000000  GICv3 redistributors (32 MiB region reserved by the framework)
0x40000000  RAM: kernel at the base, initrd above it, device tree in the last 2 MiB
```

## What Windows would need

Windows 11 on Arm does not boot from a device tree. Running it on this VMM needs:

1. **UEFI firmware.** EDK2's ArmVirtPkg, plus a flash device for its variables.
2. **ACPI tables:** MADT, GTDT, FADT, DSDT, SPCR and MCFG.
3. **A PCIe host bridge** (ECAM) with MSI through the framework's GIC.
4. **Devices Windows has drivers for:**
   - NVMe or virtio-blk for the disk
   - XHCI with a USB keyboard and tablet for input
   - a framebuffer for the display
5. **For 3D, the hard part:** a virtio-gpu device on the host side, and a Windows display driver. There is no complete open-source one today.

Steps 1 to 4 are known work, done before by QEMU. Step 5 is research.

## Origin

The first draft of `main.c` was generated by the agy agent from a written specification of the Hypervisor.framework API, taken from the macOS SDK headers. It was then reviewed, fixed and tested here:

- vCPU registers were being set from the wrong thread.
- PSCI `CPU_OFF` was clobbering `X0`.
- The GIC redistributor region overlapped the UART.

No code was taken from QEMU, Parallels or any other VMM.
